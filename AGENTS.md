# Notes for contributors and coding agents

## Guard decisions with local-only fields stay on this machine

Some fields are sealed into a guard decision's `asg_payload` only so that later checks on the same
machine can match against it. They are listed once, in `LOCAL_ONLY_PAYLOAD_FIELDS`
(`python/capsule_engine/guards/capsule.py`): the deal an act was checked in, the item a sale is about,
what a money-in record returns and reverses, and the digest of a caller's equivalence key (the raw
key is never sealed; an order or invoice number is guessable from its digest). Those values can
describe deals with other counterparties, so a decision capsule carrying any of them never enters an artifact made for
another party. The fields cannot be stripped from a sealed capsule, because `capsule_id` covers
them. So every export path refuses such records, naming the fields and the record count and never
a value. Today those paths are `capsule bundle` (the bundle file and its verify link) and
`capsule guard dry-run --share` (the report file). `python/tests/test_local_only_payload_fields.py` enforces this.

One value is local-only by its prefix rather than its field: a `target` starting with
`LOCAL_ONLY_TARGET_PREFIX` (`payee-fp:hmac-sha256-profile-key:`, beside the field list). That is a
payee keyed per profile, one value for one merchant across all of a profile's deals, so it links
them. The same refusal names `target` for it; a per-deal target is not refused.
`python/tests/test_payee_fp_profile.py` enforces this.

Adding a field to `LOCAL_ONLY_PAYLOAD_FIELDS`, sealing a new locally matched field on a decision,
or adding a path that exports decision capsules needs the share boundary reviewed. A new export
path calls `local_only_refusal` and gets a test in that file.

The Go guard (`go/`) holds to the same boundary. It seals no decision capsule and exports none:
it decides, and its caller seals. `RecordFor` builds an in-memory record for the ledger the next
check reads. The profile-keyed payee target that `go/guard/record.go` builds is matched locally
and never appears in a reason or a report value; `go/guard/local_only_test.go` enforces this. A
Go path added later that writes report or bundle output for another party needs the same
share-boundary review, and a test that it refuses local-only fields, as a Python one does.

## The Go guard and the Python guard ship together

`go/` is the Go implementation of this repo's guard, and the Python package is the reference. A
wicket or fold change lands in one PR with both implementations. CI (`conformance`) checks the
embedded packs and the ported definitions against the catalog, and decides the shared vectors
(`conformance-vectors/guard/v0`) with both: Python at the PR's head must write every expected
decision as committed, and Go must decide each the same, apart from the cases pinned in
`KNOWN-DIFFERENCES.json`. A behavior change re-writes the vectors
(`python scripts/conformance_vectors.py --write`) and changes Go in the same PR. When a served
pack cuts a new version, run `scripts/generate_go_packs.py` and then `--write`, which moves every
case to the new version, and re-pin any known difference that moved. A new check, or a
new version of one, needs a case that runs it, because the coverage gate fails otherwise. `go/packs/`,
`go/packs/embed.go`, `go/pack/registry_gen.go` and
`go/guard/testdata/engine-definitions.json` are generated by `scripts/generate_go_packs.py`; run
it whenever a served pack (everyday, seller) cuts a new version. Each pack's `pack.yaml` has one
source: the catalog for the current version, and the `go/packs/<pack>-<version>` directory for a
frozen one. The copies under `python/tests/fixtures/packs/` must match `go/packs` byte for
byte, and `generate_go_packs.py --check` fails CI on any drift. The design is
`docs/design/go-guard-module.md`.
